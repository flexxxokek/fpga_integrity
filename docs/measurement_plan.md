# Методика измерений и анализа

## 1. Метрики

### Статические

| Метрика | Источник |
|---------|----------|
| gate-equivalent cells / FF | Yosys `synth -noabc`, `make synth` — доступно сейчас |
| LUT / FF / BRAM / DSP | utilization report вендорной САПР — после этапа 3 |
| Fmax, WNS | static timing analysis — после этапа 3 |
| Латентность (такты) | RTL + подтверждение тестом `test_wrapper.latency` |

Результаты Yosys — gate-equivalent прокси, не вендорные LUT: `make synth`
применяет одинаковый flow ко всем ядрам, поэтому столбцы сравнимы между
собой, но не могут заменить реальный utilization report. Fmax намеренно не
выдумывается.

### Динамические (из стенда на плате)

| Метрика | Как измеряется |
|---------|----------------|
| Пропускная способность | байты / такты: счётчики `bytes` и `cycles` на lane (`bytes_per_tick`, `ticks_per_byte`) |
| Латентность генерации/проверки | счётчики тактов от `tlast` входа до `tag_valid`/`tag_error` |
| Обнаружение ошибок | счётчики TP / FN / FP на кампанию; `undetected_rate = missed / corrupted`, `false_rate = false / packets` |
| Научные генераторы искажений | Gilbert–Elliott (MODE=5 в RTL) и адверсариальные векторы HDLen — [docs/false_rate.md](false_rate.md) |
| Накладные расходы тега | `TAG_BYTES` на пакет |

## 2. Методика статических измерений

- Каждое ядро синтезируется **отдельно** (out-of-context) с одинаковыми
  constraints и одинаковым `DATA_WIDTH` — чтобы стенд не искажал сравнение.
- Sweep по `DATA_WIDTH ∈ {8, 32, 64}`.
- Сборка стенда целиком — отдельная строка в результатах.
- Кристалл, САПР и целевая частота фиксируются в [board.md](board.md).
  Результаты до получения платы помечаются как предварительные.

## 3. Кампании на плате

Стенд прогоняет одинаковые кампании для всех алгоритмов (одинаковый seed,
одинаковые пакеты и искажения):

| Кампания | Искажение | Пакетов (по умолчанию) |
|----------|-----------|------------------------|
| clean | нет | 10 000 |
| single_bit | 1 случайный бит | 10 000 |
| burst_L | burst длиной L ∈ {2, 4, 8, 16, 24, 32, 40} | 2 000 на L |
| byte_swap | перестановка двух байтов | 2 000 |
| zero_insert | вставка нулевых байтов | 2 000 |
| gilbert_elliott | пакетный канал (MODE=5) | 256 |
| tag_corruption | искажение байтов тега (MODE=9) | 256 |

Счётчики на lane: `packets_total`, `packets_corrupted`, `errors_detected` (TP),
`errors_missed` (FN), `false_alarms` (FP), `cycles`, `bytes`, `latency_sum/max`.

`cycles` — такты, в которых lane занят обработкой потока (приём beat,
финализация тега в TX/RX, выдача пакета). Простои, когда широковещательный
регистр ждёт готовности другой lane, не учитываются: так скорость каждого
метода измеряется независимо от самого медленного соседа в стенде.

## 4. Протокол обмена с хостом

Текстовый, построчный (UART, по умолчанию 115200 8N1):

- Команда: `RUN,<campaign>,<seed>,<n_packets>,<len_min>,<len_max>`
- Ответ: `RESULT,<algo>,<campaign>,<metric>,<value>` (по строке на метрику)
- Завершение: `DONE,<campaign>`; ошибка: `ERR,<code>`

Формат сознательно простой и board-независимый; финальные параметры UART —
после получения платы.

В симуляции и на этапе bring-up `report_uart` выдаёт упрощённый вариант
(одна строка на lane, затем `DONE`), который `scripts/collect.py` принимает
наравне с базовым протоколом:

```
RESULT,<lane>,<packets>,<corrupted>,<detected>,<missed>,<false>,<bytes>,<cycles>
DONE
```

Поля `bytes` и `cycles` несут метрики скорости; `collect.py` понимает как
8-символьные hex-поля от `report_uart`, так и десятичные поля старых логов.
В симуляции тест `tb/test_harness.py` пишет те же строки в файл из переменной
окружения `SIM_REPORT_LOG`, не дожидаясь UART.

## 5. Сбор и анализ данных

1. `scripts/collect.py` — приём строк по UART → `data/<date>_<board>.csv`.
2. `scripts/parse_reports.py` — статические метрики из отчётов САПР → CSV.
3. `scripts/analyze.py` — таблицы и графики → `docs/results/`; дополнительно
   вычисляет `bytes_per_tick`, `ticks_per_byte` и `ticks_per_packet`.

До появления платы тот же конвейер запускается на симуляторе:

```bash
make sim-measure-all   # кампании clean для DATA_WIDTH=8 и 32, seed 0x12345678
# или одна ширина:
make sim-measure SIM_WIDTH=32
```

Результаты: `data/sim_clean_w{8,32}.log` (строки `RESULT`),
`data/sim_clean_w{8,32}.csv` и сводная таблица `docs/results/summary.md`.

В шапке каждого набора данных: git-хэш, seed, параметры кампаний, плата, САПР.
Результаты на плате сверяются с референсом из симуляции (должны совпадать).

## 6. Итоговые таблицы и графики

- Обнаружение ошибок (% TP) vs тип искажения — по алгоритмам.
- % TP vs длина burst — подтверждение гарантии CRC (≤ CRC_WIDTH).
- LUT/FF vs `DATA_WIDTH` — по алгоритмам.
- Fmax и пропускная способность vs `DATA_WIDTH`.
- Латентность и накладные расходы тега — по алгоритмам.
- Сводная таблица «алгоритм × метрика» и выводы о применимости.

## 7. Ожидаемые выводы (гипотезы для проверки)

- CRC — лучший баланс затрат/скорости/обнаружения для аппаратной реализации.
- checksum/parity дешевы, но слепы к структурным искажениям.
- Fletcher/Adler занимают промежуточное положение; modulo-редукция удорожает логику.
- SHA-256 обнаруживает всё в рамках кампаний, но на порядки дороже и медленнее.
